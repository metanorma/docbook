# Fix Ferrum Browser-Launch Flake in CI Integration Specs

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Eliminate the recurring `Ferrum::ProcessTimeoutError` ("Browser did not produce websocket url within 10 seconds") CI failure by raising the browser process-launch timeout and retrying the one-time Chrome boot.

**Architecture:** One-file change to `spec/integration/integration_helper.rb`: pass `process_timeout: 60` to the Cuprite driver, and pre-boot Chrome once in `before(:suite)` with up to 3 attempts, logging Chrome's stderr (`ProcessTimeoutError#output`) between attempts.

**Tech Stack:** RSpec, Capybara, Cuprite 0.17, Ferrum 0.17.2, headless Chrome on GitHub Actions.

## Global Constraints

- Touch ONLY `spec/integration/integration_helper.rb` (plus this plan file).
- No changes to `.github/workflows/*` — they are auto-generated by Cimas ("Do not edit it manually").
- No extra Chrome flags — Ferrum's `DEFAULT_OPTIONS` already includes `disable-dev-shm-usage` and the standard CI-hardening set (verified in ferrum-0.17.2 `lib/ferrum/browser/options/chrome.rb`).
- The warm-up must not run on Windows (`Gem.win_platform?`) or when the frontend is not built — integration specs are skipped in both cases.

## Root Cause (evidence, not conjecture)

1. The failing example, `reader_features_spec.rb:81`, is the **first feature example in the whole suite** (spec files load alphabetically: `integration/reader_features_spec.rb` before `integration/reader_spec.rb`; no random ordering is configured in `spec_helper.rb`). Its first `visit` triggers Cuprite's **lazy Chrome spawn** (`Capybara::Cuprite::Driver#browser` → `@browser ||= Browser.new(@options)`).
2. Ferrum 0.17.2 defaults `process_timeout` to **10 seconds** (`PROCESS_TIMEOUT = ENV.fetch("FERRUM_PROCESS_TIMEOUT", 10).to_i`, `lib/ferrum/browser/options.rb:11`). The repo's driver registration passes no override.
3. On a loaded GitHub Actions runner (suite = 1009 examples; npm build + docbook HTML build precede the first visit), Chrome cold start can exceed 10 s → `parse_ws_url` raises `ProcessTimeoutError` (`lib/ferrum/browser/process.rb:105,171`) — exactly the CI stack trace.
4. **Reproduced locally:** `FERRUM_PROCESS_TIMEOUT=0 bundle exec rspec spec/integration/reader_features_spec.rb:81` fails with the identical exception, message, and stack; the same command without the env var passes.
5. All prior fix attempts (commits `f7f364b`, `8292110`, `4564c91`, `d835096`, `e15a845`, `5f69baa`) changed **test logic** (waits, `execute_script`, CI skips). None touched the **process-launch timeout**, which is why the flake kept returning.

Two failure modes exist for launch:
- (a) Chrome is slow to boot under CI load → fixed by a larger `process_timeout` (60 s).
- (b) Chrome dies at startup and never prints the DevTools URL → no timeout helps; only a **fresh launch attempt** recovers. `Cuprite::Driver#browser` does not memoize when `Browser.new` raises, so simply calling it again performs a clean relaunch.

The fix covers both modes: 60 s timeout + up to 3 boot attempts, with Chrome's captured stderr (`e.output`) warned between attempts so any residual failure is diagnosable from CI logs instead of mysterious.

- [ ] **Step 2: Pass `process_timeout: 60` to the driver and add the warm-up**

Replace `spec/integration/integration_helper.rb:20-29` (driver registration) with:

```ruby
if frontend_built?
  Capybara.register_driver :cuprite do |app|
    Capybara::Cuprite::Driver.new(app, headless: true,
                                       process_timeout: 60,
                                       timeout: 15,
                                       browser_options: { "no-sandbox": nil })
  end

  Capybara.default_driver = :cuprite
  Capybara.app_host = "file://"
  Capybara.default_max_wait_time = 10
end

# Chrome's one-time launch is the flakiest step on CI runners: under load the
# DevTools websocket URL can take longer than Ferrum's timeout, and a crashed
# launch never produces it at all. Booting here, with retries, keeps that
# failure mode out of the first feature spec.
def boot_browser_with_retries(attempts: 3)
  Capybara.current_session.driver.browser
rescue Ferrum::ProcessTimeoutError => e
  attempts -= 1
  raise if attempts.zero?

  warn "Chrome launch timed out (#{attempts} attempts left). Chrome output: #{e.output}"
  retry
end
```

- [ ] **Step 6: Verify the retry path end-to-end with a one-off failure injection**

Write `<scratchpad>/fail_first_launch.rb`:

```ruby
# Forces the FIRST Chrome launch to raise Ferrum::ProcessTimeoutError,
# proving the before(:suite) warm-up retries and the suite still passes.
require "capybara/cuprite"

module FailFirstLaunch
  @failed = false

  def self.arm!
    Capybara::Cuprite::Browser.singleton_class.prepend(Module.new do
      def new(options)
        unless FailFirstLaunch.tripped?
          FailFirstLaunch.trip!
          raise Ferrum::ProcessTimeoutError.new(10, "injected launch failure")
        end
        super
      end
    end)
  end

  def self.tripped? = @failed
  def self.trip! = @failed = true
end

FailFirstLaunch.arm!
```

Run: `bundle exec rspec -r <scratchpad>/fail_first_launch.rb spec/integration/reader_features_spec.rb`
Expected: stderr shows `Chrome launch timed out (2 attempts left). Chrome output: injected launch failure`, and ALL examples PASS.
